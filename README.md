Небольшое веб-приложение для промо-акции. Покупатель регистрирует кассовый чек, модератор проверяет его в админке и принимает или отклоняет (с причиной). Сделано как тестовое задание

**Стек:** Python 3.13, Django 5.2, PostgreSQL 16, Redis 7, gunicorn, WhiteNoise, Docker Compose. Фронтенд - серверные шаблоны Django и чистый JS

## Как запустить
ВАЖНО - для запуска на Windows нужен Docker Desktop
```bash
cp .env.example .env     # (можно пропустить: возьмутся значения из .env.example)
docker compose up --build # (или docker compose up -d, чтобы не выводить логи)
```

Сайт откроется на <http://localhost:8000>.

| Что | Адрес |
|---|---|
| Регистрация участника | <http://localhost:8000/accounts/signup/> |
| Личный кабинет | <http://localhost:8000/> (после входа) |
| Админка модератора | <http://localhost:8000/admin/> |
| API | <http://localhost:8000/api/receipts/> (нужна сессия участника) |

**Про админа.** При первом запуске автоматически создаётся модератор: логин `admin`, пароль `admin-dev-password` (берётся из `DJANGO_SUPERUSER_*` в `.env`). Это dev-значения, лежащие в репозитории. Если пользователь `admin` уже существует, повторно он не создаётся

### Настройки (.env)

| Переменная | Что делает                                                   |
|---|--------------------------------------------------------------|
| `PROMO_START_DATE`, `PROMO_END_DATE` | Период акции, включительно, формат `YYYY-MM-DD`. Обязательны! |
| `PROMO_MIN_AMOUNT` | Минимальная сумма чека (1000)                                |
| `RECEIPT_MAX_RESUBMISSIONS` | Сколько раз можно повторно отправить отклонённый чек (2)     |
| `RECEIPT_PHOTO_MAX_MB` | Максимальный размер фото                                     |
| `RECEIPT_SUBMIT_RATE_LIMIT` | Количество попыток регистрации в минуту на пользователя      |
| `RECEIPT_STATUS_POLL_SECONDS` | Как часто кабинет обновляет статусы "на проверке"             |
| `DJANGO_SUPERUSER_*` | Первый модератор                                             |

## Что сделано по ТЗ

- **Пользователи** - стандартный `django.contrib.auth`: вход и выход как есть, плюс простая регистрация и страница профиля. Модератор - обычный пользователь с флагом `is_staff`
- **Модель чека** - ФН, ФД, ФП, дата и время покупки, сумма, статус (на проверке / принят / отклонён), причина отказа, пользователь, дата регистрации
- **Регистрация чека** с проверками на сервере:
  - дата покупки в периоде акции;
  - сумма не меньше 1000 ₽;
  - связка ФН + ФД + ФП уникальна: при повторе пользователь видит понятное сообщение, а не 500;
  - новый чек всегда "на проверке"
- **Личный кабинет** - свои чеки от новых к старым, по 10 на странице: дата покупки, сумма, статус, причина отказа. Кнопка "Зарегистрировать чек" ведёт на форму
- **Админка** - стандартная, модератор меняет статус
- **API** - `GET /api/receipts/` отдаёт чеки текущего пользователя в JSON. Выборка всегда начинается с "чеки этого пользователя"
- **Фронтенд** - по макету Figma: структура блоков, состав и порядок полей, цвета, шрифты. Период акции выводится из настроек. JS проверяет обязательные поля и форматы до отправки, ошибки подсвечиваются у полей, отправка идёт через `fetch`, успех и ошибка выглядят по-разному. Форма работает и без JS (через обычный POST)
- **Инфраструктура** - `docker compose up` поднимает всё вместе с Postgres и Redis, есть `.env.example`.

## Что добавил сверх ТЗ
- **Тесты** - валидаторы (границы периода, сумма 999.99 и 1000, форматы ФН/ФД/ФП), сервисы (новый чек всегда "на проверке", дубль, повторная отправка, ограничения в БД) и API (чужие чеки не отдаются)
- **Фото чека** - формат проверяется по содержимому, а не по расширению, размер ограничен настройкой. Фото хранится под случайным именем и отдаётся только владельцу и модератору
- **Строка из QR-кода** - можно вставить строку из QR на чеке, и поля формы заполнятся сами. Распознавание QR прямо с фото есть только там, где браузер умеет `BarcodeDetector`
- **Повторная отправка отклонённого чека**
- **Ограничение частоты** - регистрации через Redis
- **Обновление статусов без перезагрузки** - кабинет опрашивает API только по чекам "на проверке" и только пока вкладка открыта
- **Сортировка по колонкам**
- **Страница "Правила"** с периодом и минимальной суммой
- **Журнал смены статусов** - кто и когда поменял статус и почему, пишется только в БД (в админке не показывается)

## Спорные места и как я их решил

### Можно ли отправить заново отклонённый чек?
Да, но только владельцу и ограниченное число раз

Чеки отклоняют по разным причинам: опечатку в сумме или нечитаемое фото можно исправить, поэтому запретить повтор совсем означает наказать человека за опечатку. Разрешить без ограничений = дать возможность спамить одним чеком, из-за этого лимит

Как это работает:
- уникальность ФН + ФД + ФП абсолютная, и в коде, и уникальным ограничением в БД;
- при повторной отправке обновляется та же запись: статус снова "на проверке", причина очищается, обновляются данные;
- чужой чек зарегистрировать нельзя ни в каком статусе ("уже зарегистрирован другим участником");
- свой чек "на проверке" или принятый отправить повторно нельзя;
- когда лимит исчерпан, пользователь видит сообщение. Модератор может вернуть чек на проверку вручную в админке

### Часовые пояса и границы периода
На чеке печатается местное время кассы, а часового пояса магазина в данных чека нет. Покупатель с дальнего Востока, который купил что-то в 23:00 последнего дня акции, держит чек именно с этой датой и ждёт, что он участвует, 
поэтому период задан календарными датами включительно и сравнивается с датой, напечатанной на чеке, независимо от пояса пользователя и сервера

Дату "в будущем" отсекаю с запасом на самый восточный пояс: время на чеке не может быть позже, чем сейчас по UTC+14
`TIME_ZONE` влияет только на отображение служебных дат, но не на то, попадает ли чек в акцию
Альтернативу "считать по часовому поясу пользователя" я отверг: пояс браузера не равен поясу магазина, и решение "участвует ли чек" зависело бы от того, откуда его вводят

### Остальные решения

- ФД и ФП хранятся числами, так `00123` и `123` считаются одним чеком. ФН — строка ровно из 16 цифр
- Сумма принимается как `1500`, `1 500,50` или `1500.5`, максимум два знака после запятой
- Модератор не правит данные чека, только статус и причину
- Чеки нельзя создавать в админке, только через обычную регистрацию
- Участника, у которого есть чеки, нельзя удалить
- Анонимный запрос к API получает `401` в JSON, а не редирект на страницу входа

## Чего нет

- Проверки чеков через ФНС, т.к. данный проект является тестовым
- Подтверждения email и восстановления пароля по почте, можно добавить настройки тестовой почты и по SMTP отправлять данные
- Отдельной вёрстки страниц смены пароля
- Тестов фронтенда

## Структура

```
config/      настройки (всё из окружения), urls
core/        общий шаблон, страница правил
accounts/    регистрация и профиль
receipts/
  models.py       модели чека
  validators.py   правила проверки чека
  forms.py        формы регистрации и модерации
  services.py     вся запись в БД
  selectors.py    чеки пользователя
  views.py        кабинет, регистрация, фото
  api.py          /api/receipts/
  admin.py        модерация
static/js/   проверка формы, отправка через fetch, обновление статусов
templates/   шаблоны
```
